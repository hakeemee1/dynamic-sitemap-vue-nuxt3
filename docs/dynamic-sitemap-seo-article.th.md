# ทำไม "sitemap ไม่มี URL สินค้า" ถึงเป็นปัญหา SEO (และวิธีแก้)

*บทความสำหรับแชร์ความรู้ภายในทีม ใช้ตัวอย่างทั่วไปเท่านั้น — ไม่มีการอ้างอิงถึงลูกค้าจริง โดเมนจริง
หรือ production URL ใดๆ ในบทความนี้ มี proof-of-concept ที่รันได้จริงประกอบบทความนี้ แต่ไม่จำเป็นต้อง
รันโค้ดก็เข้าใจเนื้อหาได้*

## ปัญหา แบบเข้าใจง่าย

sitemap คือรายการ URL ที่เว็บไซต์ส่งให้ search engine โดยบอกว่า "นี่คือทุกอย่างที่ควรค่าแก่การ index"
search engine ไม่ได้เชื่อ sitemap แบบไม่ตั้งคำถาม แต่ก็ใช้มันเป็นตัวช่วยสำคัญในการจัดลำดับความสำคัญว่า
จะ crawl หน้าไหนก่อน โดยเฉพาะหน้าที่ยากจะค้นเจอผ่านการตามลิงก์เพียงอย่างเดียว

frontend อีคอมเมิร์ซที่ใช้ Nuxt ของเราหลายตัวสร้าง `sitemap.xml` อัตโนมัติผ่านโมดูล sitemap ที่สแกน
route แบบ file-based ของแอป วิธีนี้ใช้ได้ดีกับหน้าอย่างหน้าแรก หน้ารายการหมวดหมู่ หรือหน้าแคมเปญ
เพราะแต่ละหน้ามีไฟล์และ URL path เป็นของตัวเอง

แต่วิธีนี้ **ใช้ไม่ได้** กับหน้ารายละเอียดสินค้าที่ถูกเรียกผ่าน query string เช่น
`/products/detail?product_id=123` แทนที่จะเป็น `/products/123` ซึ่งเป็น routing pattern ที่ frontend
จริงบางตัวของเราใช้อยู่แล้ว ในมุมมองของโมดูล sitemap `/products/detail` คือ route เดียว มันไม่มีทาง
รู้ว่า `product_id=123`, `product_id=456` และค่าอื่นๆ อีกนับพันคือสินค้าแยกกันที่ควร index ผลลัพธ์คือ
sitemap มีแค่หน้าระดับบนไม่กี่หน้า และ **ไม่มี URL สินค้าแม้แต่รายการเดียว**

### ทำไมเรื่องนี้ถึงสำคัญต่อ SEO

หน้ารายละเอียดสินค้าแต่ละหน้าคือหน้าที่มีโอกาสติดอันดับสูงสุดสำหรับการค้นหาที่เจาะจงและมี intent สูง
(เช่น "เสื้อยืดคอกลมสีกรมท่า ไซส์ M" ไม่ใช่แค่ "ร้านเสื้อผ้า") ถ้า search engine ค้นหา URL เหล่านี้ผ่าน
sitemap ไม่เจอ — ซึ่งเป็นช่องทางที่ออกแบบมาเพื่อช่วยให้ crawler เจอหน้าที่อาจพลาดไปโดยเฉพาะ — ก็อาจ
ใช้เวลานานกว่ามากในการ index หรือบางหน้าอาจไม่ถูก index เลย โดยเฉพาะกับแคตตาล็อกขนาดใหญ่ ยิ่งหน้า
สินค้าถูก index น้อยเท่าไร โอกาสที่จะปรากฏในผลการค้นหาสำหรับสิ่งที่คนกำลังค้นหาจริงๆ ก็ยิ่งน้อยลงเท่านั้น

## ก่อน / หลัง: หน้าตาของการแก้ไข

นี่คือตัวอย่าง sitemap "ก่อนแก้" แบบย่อ สำหรับแคตตาล็อกเล็กๆ ที่ใช้ query-string pattern ข้างต้น
สร้างขึ้นโดยไม่มีการปรับแต่งใดๆ — คือผลลัพธ์ default ของโมดูล sitemap ที่สแกน route จากไฟล์:

```xml
<url><loc>https://example-shop.test/</loc></url>
<url><loc>https://example-shop.test/products</loc></url>
<url><loc>https://example-shop.test/campaigns/summer-sale</loc></url>
```

มีแค่ 3 URL ไม่มีสักอันที่เป็นสินค้า สินค้าทุกชิ้นในเว็บไซต์มองไม่เห็นใน sitemap นี้เลย

นี่คือแคตตาล็อกเดียวกัน แต่เพิ่ม logic เล็กน้อยเข้าไป — เป็น hook ที่ดึงแคตตาล็อกสินค้ามาแล้วสร้าง
sitemap entry หนึ่งรายการต่อสินค้าหนึ่งชิ้น:

```xml
<url><loc>https://example-shop.test/products/detail?product_id=42</loc></url>
<url><loc>https://example-shop.test/products/detail?product_id=43</loc></url>
```

ตอนนี้สินค้าทุกชิ้นมี entry เป็นของตัวเอง กลไกคือการ hook เข้าไปในขั้นตอนสร้าง URL ของโมดูล sitemap:
ดึงรายการสินค้าจาก backend เดียวกับที่เว็บไซต์ใช้อยู่แล้ว แปลงสินค้าแต่ละชิ้นเป็น canonical URL แล้วส่ง
ผลลัพธ์ให้โมดูล sitemap รวมกับ route ที่มันค้นพบเองตามปกติ

## ไม่ใช่แค่ "เพิ่ม URL" — canonical URL ก็สำคัญเช่นกัน

หน้ารายละเอียดสินค้าจริงมักไม่ได้รับแค่ query parameter เดียว มันอาจรับ `category`,
`bundle` id ที่ใช้สำหรับลิงก์โปรโมชัน หรือ `status` flag สำหรับพรีวิวภายในได้อย่างถูกต้องตามปกติ
คนหนึ่งคนอาจเข้าถึงสินค้า *ชิ้นเดียวกัน* ผ่าน URL ที่ต่างกันได้หลายแบบ:

```text
/products/detail?product_id=42
/products/detail?product_id=42&category=shirts
/products/detail?product_id=42&category=shirts&bundle=summer-promo
```

ถ้าวิธีแก้แบบง่ายๆ เกินไปแค่ก็อปพารามิเตอร์ทุกตัวที่มีอยู่ในข้อมูลสินค้ามาใส่ sitemap ตรงๆ sitemap
อาจจบลงด้วยการมี URL ที่เกือบซ้ำกันหลายอันสำหรับหน้าเดียวกัน นี่คือต้นทุนที่เกิดขึ้นจริง ไม่ใช่แค่ความ
ซ้ำซ้อนที่ไม่มีผลกระทบ: search engine จะแบ่ง ranking signal — ลิงก์, การคลิก, ความเกี่ยวข้อง —
กระจายไปตาม URL ทุกอันที่มันเคยเห็นสำหรับหน้านั้น เมื่อกระจายไปยัง URL ที่เกือบซ้ำกัน 3 อัน แทนที่จะ
รวมไว้ที่อันเดียว แต่ละเวอร์ชันก็จะดูอ่อนแอกว่าที่สินค้าชิ้นนั้นควรจะเป็น ซึ่งส่งผลเสียต่ออันดับการค้นหา

ดังนั้นการแก้ไขที่ถูกต้องจึงไม่ใช่แค่ "แสดงรายการสินค้า" แต่คือ "แสดงสินค้าแต่ละชิ้นแค่ครั้งเดียว ที่
canonical URL เดียวของมัน" ในกรณีของ query-string หมายความว่า sitemap entry จะเก็บไว้แค่พารามิเตอร์
ที่ใช้ระบุตัวสินค้าจริงๆ (`product_id`) แล้วตัดที่เหลือทิ้งทั้งหมด ไม่ว่าข้อมูลสินค้าที่แท้จริงจะมีฟิลด์
อื่นติดมาด้วยกี่ตัวก็ตาม ความครอบคลุม (coverage) และการทำให้เป็น canonical เป็นสองส่วนที่ต้องมีคู่กัน
ใน sitemap ที่ถูกต้อง แก้แค่อย่างใดอย่างหนึ่งโดยไม่แก้อีกอย่างก็ยังเสียโอกาสอยู่ดี

## ปัญหาที่สอง ที่เกี่ยวข้องกัน: เว็บไซต์หลายภาษาที่ไม่มี URL แยกตามภาษา

เว็บไซต์ที่มีมากกว่าหนึ่งภาษาจะมีอีกชั้นหนึ่งเพิ่มเข้ามา: ผู้เข้าชมที่พูดภาษาฝรั่งเศสและผู้เข้าชมที่พูด
ภาษาไทยที่ค้นหาสินค้าชิ้นเดียวกัน ควรจะไปหน้าเวอร์ชันภาษาของตัวเอง ไม่ใช่ผลลัพธ์ที่ไม่ตรงภาษาหรือดู
เหมือนซ้ำกัน search engine ใช้ `hreflang` annotation เป็นหลักในการตัดสินใจเรื่องนี้ — เป็นลิงก์ต่อภาษา
ที่บอก crawler ว่า "หน้านี้มีเวอร์ชันภาษา X อยู่ที่ URL อีกอันนี้" ซึ่งสิ่งสำคัญคือกลไกนี้จะใช้ได้ก็ต่อเมื่อ
แต่ละภาษามี URL *เป็นของตัวเอง* จริงๆ เท่านั้น

frontend ของเราตอนนี้สลับภาษาด้วยวิธีที่ต่างออกไป: ใช้ URL เดียวต่อหนึ่งหน้า โดยอ่านภาษาที่ใช้งานอยู่
กลับมาจาก cookie (`i18n_redirected`) แทนที่จะมาจากตัว URL เอง ซึ่งเป็นทางเลือกที่สมเหตุสมผลดีสำหรับ
ประสบการณ์การใช้งาน — ผู้เข้าชมที่กลับมาใหม่จะได้ภาษาของตัวเองอัตโนมัติ โดยไม่มี prefix `/en/` มา
รก address bar แต่มันมีผลข้างเคียงที่พลาดง่าย: crawler ไม่ได้พก cookie ติดตัวไปในแต่ละ request มันไม่มี
ภาษาที่จำไว้เลย ดังนั้นทุกครั้งที่มันขอ `/products/detail?product_id=42` มันจะได้รับเนื้อหาภาษา
*default* เสมอ ส่วนเนื้อหาภาษาอื่นที่ไม่ใช่ default บน URL เดียวกันนี้ ในแง่ของการ index จึงมองไม่เห็น
เลย — เพราะไม่มี URL แยกให้มัน index อยู่

พูดให้เป็นรูปธรรม หมายความว่า pattern นี้สร้าง `hreflang` annotation ไม่ได้เลย เพราะไม่มี URL ที่สอง
ให้ alternate ชี้ไปหา นี่คือช่องโหว่ SEO ที่สอง ที่เกิดขึ้นจริง อยู่คู่กันกับปัญหา URL สินค้าหายไป —
ไม่ใช่บั๊กของการแก้ sitemap แต่เป็นข้อจำกัดของการเลือก routing แบบนี้ตั้งแต่ต้น ซึ่งการแก้ sitemap เอง
แก้ให้ไม่ได้ การจะแก้ปัญหานี้จริงๆ ต้องให้แต่ละภาษามี URL เป็นของตัวเอง (ผ่าน prefix, subdomain,
หรือ query parameter) ซึ่งเป็นการเปลี่ยน routing ที่ใหญ่กว่าขอบเขตของ POC นี้ แต่ควรรู้ไว้ ก่อนจะสรุป
เอาเองว่า "sitemap แก้แล้ว" หมายความว่า "เว็บไซต์หลายภาษานี้ index ได้ครบสมบูรณ์แล้ว"

## ข้อสังเกตเรื่องความสด: SSR เทียบกับ static generation

sitemap จะ "สด" แค่ไหนขึ้นอยู่กับวิธี render เว็บไซต์ ในโหมด server-rendered (SSR) — ซึ่งเป็นวิธีที่
POC นี้และ frontend production ส่วนใหญ่ของเราใช้ — `/sitemap.xml` จะถูกคำนวณใหม่ทุกครั้งที่มี
request เข้ามา เพิ่มหรือลบสินค้าเมื่อไร request ถัดไปที่เรียก sitemap ก็จะสะท้อนการเปลี่ยนแปลงนั้น
ทันที

เว็บไซต์ที่ใช้ static generation (SSG) ทำงานต่างออกไป: sitemap เป็นแค่ภาพสแนปช็อตที่ถ่ายไว้ตอน
build ถ้าแคตตาล็อกเปลี่ยนแปลงหลังจากนั้น sitemap จะไม่รู้เลยจนกว่าจะ build และ deploy ใหม่ วิธีนี้
เป็นแนวทางที่ใช้ได้ แต่ต้องมีสิ่งที่ SSR ไม่จำเป็นต้องมี: กลไก trigger การ rebuild เมื่อแคตตาล็อก
เปลี่ยน (เช่น webhook จาก backend) ไม่งั้น sitemap จะเก่าไปเรื่อยๆ โดยไม่มีใครรู้ บทความนี้ไม่ได้
ลงรายละเอียดวิธีสร้างกลไกนั้น — มันเป็นโครงสร้างพื้นฐานอีกส่วนหนึ่ง — แต่ควรรู้ไว้ว่ามี tradeoff นี้อยู่
ก่อนจะเลือกใช้ SSG กับแคตตาล็อกที่เปลี่ยนแปลงบ่อย

## สิ่งที่บทความนี้ไม่ครอบคลุม

POC และบทความนี้จงใจไม่พูดถึงหลายเรื่องที่การนำไปใช้จริงในระดับ production จะต้องจัดการเพิ่มเติม:

- **Sitemap chunking / sitemap index file** sitemap มีข้อจำกัดขนาดไฟล์/จำนวน entry ต่อไฟล์
  แคตตาล็อกที่มีสินค้าหลักหมื่นชิ้นต้องแบ่งเป็นหลายไฟล์ sitemap โดยอ้างอิงผ่าน sitemap index —
  เป็นประเด็นจริงสำหรับแคตตาล็อกขนาดใหญ่ แต่ไม่ได้จำลองไว้ในนี้
- **route แบบ query-string อื่นๆ** ครอบคลุมแค่หน้ารายละเอียดสินค้าหลักเท่านั้น แคตตาล็อกจริงมักมี
  หน้าที่ใช้ query-string routing อื่นเพิ่มเติม (หน้า variant/attribute ของสินค้า, หน้า flash-sale
  ฯลฯ) ที่ต้องใช้แนวทางเดียวกันนี้
- **การเชื่อมต่อ backend จริง** POC นี้ใช้ mock product list แบบ static ขนาดเล็กแทน product API
  จริง
- **การ deploy หรือการตรวจสอบแบบจริง** เช่นผ่าน Google Search Console หรือ URL Inspection tool
  — POC นี้สาธิตแบบ local เท่านั้น
- **canonical tag บนหน้าเว็บ** บทความและ POC นี้พูดถึงการทำ canonicalization ฝั่ง sitemap
  เท่านั้น ส่วนแท็ก `<link rel="canonical">` บนหน้าสินค้าเองเป็นการแก้ไขอีกเรื่องที่เกี่ยวข้องกัน
  แต่แยกกัน
- **การให้แต่ละภาษามี URL เป็นของตัวเอง** ตามที่อธิบายไว้ด้านบน POC นี้จงใจคงรูปแบบเดิมไว้ คือใช้
  cookie กำหนดภาษาบน URL เดียว ตามที่ frontend ของเราใช้อยู่จริง และไม่ได้ implement `hreflang`
  หรือวิธีแก้ใดๆ สำหรับช่องโหว่เรื่อง indexability ที่เกิดจากรูปแบบนี้

## สรุป

ถ้า frontend ไหนใช้ query string ในการ route ไปยังเนื้อหาที่ควรถูก index อย่าสมมติเอาเองว่าโมดูล
sitemap มองเห็นมัน — ต้องตรวจสอบ และเมื่อจะแก้ ต้องแน่ใจว่าการแก้นั้นทำให้แต่ละหน้ามี canonical
URL เดียว ไม่ใช่แค่ "เพิ่ม URL ให้มากขึ้น" — การมี coverage โดยไม่มี canonicalization อาจเป็นแค่
การแลกปัญหา SEO หนึ่งไปกับอีกปัญหาหนึ่ง จากนั้นให้ตรวจดูอีกชั้นถัดไปด้วย: ถ้าเว็บไซต์นั้นสลับภาษา
โดยไม่เปลี่ยน URL ด้วย ต้องรู้ไว้ว่าเนื้อหาภาษาที่ไม่ใช่ default บนหน้านั้นจะมองไม่เห็นสำหรับ search
engine เลย ไม่ว่า sitemap ข้างใต้จะถูกต้องแค่ไหนก็ตาม
